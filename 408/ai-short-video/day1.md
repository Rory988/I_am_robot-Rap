## day1 AI 短剧项目

定位先说死：这是一个"AI 应用工程"项目，不是"训练模型"项目。

我的贡献是把开源大模型组装成一条可重复、可控成本的生产流水线，并解决了一致性、衔接、验收这些工程问题。

#### Blackwell 架构

**Blackwell（布莱克韦尔）是英伟达继 Hopper（H100）之后新一代 GPU 架构，专门为大模型训练 + 推理而生，现在最有名的就是 B200、GB200，是现在 “AI 工厂” 的主力芯片架构**NVIDI...。

> 名字来自数学家 David Blackwell，不是显卡型号，是一套底层设计规范；就像 Hopper 是 H100 的架构，Ada 是 RTX 40 系架构。

### 第 2 层：模型层（MiniMax H3，满血 BF16 全套 123.6 GB）

| 部件                    | 体积     | 干什么的                                                     |
| ----------------------- | -------- | ------------------------------------------------------------ |
| 主干 DiT（FL2VA 版）    | 66.28 GB | 视频生成的核心：扩散 Transformer，在潜空间里逐步去噪生成画面；FL2VA = 支持首帧＋尾帧条件 |
| 文本编码器 Qwen3-VL 32B | 51.51 GB | 把提示词和参考图"翻译"成主干能懂的条件向量（多模态编码器，能看图） |
| 视频 VAE（fp16）        | 5.21 GB  | 把画面压缩进潜空间、再解码回画面。生成不在像素上做，在压缩后的潜空间做，所以算得动 |
| 音频 VAE（fp32）        | 0.61 GB  | 同理，负责 H3 自带音轨的编解码                               |
| Turbo LoRA（可选）      | 1.96 GB  | 小补丁：挂上后 8 步出片（vs 全质量 20 步），快但质量略降，正式生产关掉不用 |

关键概念（必懂）：

- ***\*扩散模型\****：从纯噪声开始，按条件一步步去噪，最终"显影"出画面。步数越多越精细、越慢。
- ***\*潜空间\****：VAE 把一帧画面压缩成小得多的数字表示，扩散在潜空间里进行，最后解码回像素
- ***\*图生视频（I2V）\****：给一张图＋提示词，模型以图为起点生成运动；本项目用它的升级版——***\*首尾帧（FL2VA）\****：同时给定起点帧和终点帧，模型补中间运动。
- ***\*量化\****：把权重精度从 BF16 降到 INT8/NVFP4，体积和显存大减、质量略降。本项目用满血 BF16；显存不够时的回退路线就是换量化权重（文本编码器 27.1 GB 的 int8 版等）。
- ***\*帧对齐\****：H3 的时长按 17k+5 帧 @24fps 对齐，所以时长不能任意填，剪辑时裁多余部分。

#####  DiT

DiT = Diffusion Transformer（扩散 Transformer）

它就是把扩散模型里面原来那个卷积 U-Net，换成 Transformer 当去噪主干；Sora都是 DiT，也是现在跑在 Blackwell 上面最火的一类生成模型。

##### Sora

OpenAI 的文本生成视频模型，属于 **DiT（Diffusion Transformer）**，把视频切成时空 patch，当成一串 token，迭代去噪生成视频，最长可以生成约一分钟连贯视频

##### 把权重精度从 BF16 降到 INT8/NVFP4

- BF16（Brain Float 16）：16 bit 浮点数
- INT8：8 位定点整数
- NVFP4（NVIDIA FP4，也就是 MXFP4）：4 bit 浮点数

“降精度” 到底在干什么？？？？？？其实这里也很好奇我问了豆包说是：

量化：把密密麻麻的实数，映射到一套更少 bit、更少刻度的编码里面；相当于把尺子的刻度变粗。

> 把权重精度从 BF16 降到 INT8 / NVFP4，体积和显存大减、质量略降

- ✔️：好处：同样一张卡，可以放下更大模型 / 同时跑更多并发；访存压力下降，吞吐量上升；Blackwell 硬件原生支持 NVFP4，算力暴涨。

- ✔️：代价：刻度粗了，数字存得不准，会引入量化误差；误差积累，最终画面、文字质量下滑。

- 一句话浓缩：

  > 降低权重表示精度，减少存储占用与访存数据量，提升推理速度与并发量；但是可表示数值变少，量化误差增大，生成结果更容易出现细节丢失、失真。

##### ComfyUI

它不是模型！它是一个**可视化的流水线调度工具 / 框架**。

- 里面是一个个「节点」：一个节点只干一件小事：加载权重、把文字交给文本编码器、VAE 编码、DiT 采样去噪、VAE 解码、保存视频……
- 你用连线把节点串起来，就规定好了：数据先去哪里、再算什么、最后输出什么。
- 之前聊的 FLUX、SD3、H3，都可以在 ComfyUI 里面跑。

类比： 模型（H3）就像一台发动机；ComfyUI 就是操作台、管道、阀门，你把发动机接在管道上，控制数据流怎么走。

> 放到 408：它本质就是任务流水线、异步调度、生产者消费者模型；各个节点就是不同的计算任务，节点之间传递张量（数据）。

##### `video_minimax_h3_i2v`（工作流）

- 工作流 = 一套已经连好线的节点模板

- `i2v` = Image to Video，图生视频，就是咱们前面说的 I2V；这个专门是给 MiniMax H3 用的。
- 这个模板已经搭好了一共 23 个节点：默认路径是：读入参考图 → 文本编码 → DiT 逐步采样去噪 → VAE 解码 → 输出视频。
- 用户只需要改两处：
  1. 在 “模型槽位” 挂上咱们前面那张表里的全套 H3 BF16 权重
  2. 修改输入：换提示词、换起始图片 剩下所有步骤自动跑，不用自己重新连线。

简单说：别人已经把完整流水线搭好了，你只需要 “塞模型 + 塞输入”。

##### Jupyter Notebook（`.ipynb`）

- 俗称格子本，把代码切成一格一格，可以一格一格单独运行。
- 和 ComfyUI 的区别：
  - ✅ **ComfyUI：图形、拖节点连线，给喜欢可视化调参的人**
  - ✅ **Jupyter：纯代码驱动，适合批量部署、自动跑实验、写脚本**

##### Cloudflare Tunnel（cloudflared 隧道）

- Colab 的虚拟机藏在内网，没有公网 IP，外面浏览器不能直接打开里面的 ComfyUI。
- **隧道作用**：在云机器主动连到 Cloudflare 的服务器，开出一条通道；给你一个临时公网网址。你在自己浏览器打开这个链接，就能远程操作这台机器上的 ComfyUI。
- **特点**：每次重启虚拟机，链接就变；不是固定地址。

#####  ffmpeg

大名鼎鼎的音视频工具。 这里用途：

- 从生成好的视频里面抽帧拿图；
- 把上一段视频的最后一帧抠出来，当做下一段视频的起始帧（刚好对应 H3 的首尾帧 FL2VA）；
- 剪掉开头结尾坏掉的死帧。 它不是 AI，只是音视频编解码、处理工具。

##### 按字节校验 + 断点续传

这个是下大模型权重必备的。

- **断点续传**：一百多 GB，如果网络断了，不用从头重新下载；下次接着上次停下的地方继续拉文件。
- **按字节校验（哈希校验）**：下载完一个文件，对比官方的哈希值，看文件有没有损坏、有没有下错；如果已经存在完好文件，直接跳过。

#### 5.1 第一次

**逐条对照这次实际做的：**

1. **关键帧先行**：只做到一半。人物定妆图是先出静图让你验收的，但每个镜头没有先出关键帧，是直接拿参考图生成视频的。
2. **一镜一动作**：剧本写了，执行时没守住。白布穿帮就是一镜塞了"宣布死亡"和"盖布"两个状态。
3. **首尾帧 + 变化链**：没用。这次用的是 ref2va（参考图生视频），不是 FL2VA（首尾帧）。
4. **链式续拍**：没用。每镜单独生成再硬拼，这是你说"把画面串起来"的那个点，还在计划里。
5. **说话人绑定**：用了，但没台词的镜头没写死"不说话"，所以混进了乱码人声。
6. **状态链与冻结描述**：人物描述固定复用做到了，但"谁在场"没管好，平哥才提前出现。
7. **三级验收**：做了抽帧加审片，但审片会判断错，最后还是靠你的眼睛。

**这次实际的全流程是这样：**

1. **定调**：定横屏 16:9、3.5 分钟、主场景宴会厅、三人站位。
2. **写剧本**：Claude 写完整因果剧本和 41 镜分镜表，Gemini 版只作参考。
3. **定妆**：Codex 出人物定妆图，你验收（平哥重出过一次）。
4. **写提示词**：每镜写英文提示词，台词标说话人，只放在场人物的参考图。
5. **生成**：ComfyUI 跑 H3 ref2va，一镜约 4–6 秒，渲染 4–6 分钟。
6. **验收**：抽帧看画面，再听声音，再给你看。
7. **剪辑**：ffmpeg 拼接，无台词镜头静音，出成片。

#### 第二次：

1. **列镜头状态表**：每个镜头写清四件事：谁在场、起点是什么样、做哪一个动作、终点是什么样。下一镜的起点就是上一镜的终点。
2. **出关键帧，你先看静图**：难镜头让 Codex 出首帧和尾帧，比如周念躺地说话、按压、看表宣布。你看图过了才生成视频，错误在这一步就挡掉，不烧显卡。
3. **用首尾帧生成**：从 ref2va （参考图生视频）换成 FL2VA（首尾帧）。给模型首帧、尾帧和提示词，它只补中间的动作，人物和场景就不会跑偏。
4. **链式串起来**：下一镜直接用上一镜实际的最后一帧当首帧，镜头之间自然衔接，就是你说的把画面串起来。
5. **在 ComfyUI 里搭节点图**：把这 11 镜做成一张像思维导图的图，每镜一组节点，末帧连到下一镜首帧，一眼能看清顺序，改哪镜动哪镜。
6. **三步验收**：先看帧，再听声音，最后连同上一镜一起看，过了再给你看。
7. **剪辑**：拼接，没台词的镜头静音，统一配宴会厅环境音。

## 二、疑问答库

#### A. 项目概述类

**Q1：介绍一下这个项目，你做了什么？** 

要点：原创横屏（16:9）都市医疗短剧《叫平哥来》，目标 3.5 分钟；目标是验证"一个人＋开源模型＋云算力＋多个 AI Agent 分工"能否跑通可重复的短剧生产流程；成果：完整因果剧本与分镜表、人物定妆图、云端部署、第一幕成片和完整踩坑记录与生产规则文档。关键词：生产流程，不是抽卡。 

（可补一句：首个测试镜是竖屏，后来按短剧平台习惯改成横屏——说明做过取舍。）

**Q2：你在项目里具体负责什么？哪些不是你做的？** 

要点（必须诚实）：模型是 MiniMax 开源的 H3、框架是 ComfyUI、部署思路参考了 EasyColab；剧本初稿、定妆图由 AI Agent（Claude、Codex）产出。我做的是：工作流组装与改造（满血权重替换、云盘持久化）、多 Agent 分工与审批流程、分镜与镜头规则、提示词与验收体系、成本核算，以及所有"这个镜头过不过"的判断。——这道题答得诚实，后面所有题都稳。

**Q3：项目最大的难点是什么？** 

要点：不是"生成"，是"可控"，分两层：

1. 叙事可控：AI 只会照提示词做，故事不按时间走，观众会以为人物"死而复生"；角色没铺垫就出场，逻辑断裂。解法：时间顺序优先、每个角色入场有铺垫、一镜一动作。
2. 画面可控：跨镜一致性（脸、服装、场景漂移）、不该出现的人出现、倒地等物理动作失真。解法：定妆图锁定人物；不在场的人不放参考图并写明"not in the room"；全身倒地改用切镜（扶额摇晃 → 物品落地特写 → 已躺好）。 下一阶段：首尾帧与链式续拍解决镜头衔接（正在做，别说成已完成）。

#### B. 模型原理类

**Q4：视频生成模型的基本原理？** 

要点：潜空间扩散——VAE 把视频压进潜空间，DiT 在文本/图像条件下逐步去噪，VAE 再解码回像素；DiT 把视频切成时空 patch 当作 token，用注意力同时建模画面内和帧与帧之间的关系，所以能保持连贯。

**Q5：为什么要用首尾帧，只给首帧不行？** 

要点：只给首帧，运动终点由模型自由发挥，情绪和动作落点不可控；首尾帧把起点终点都钉死，模型只补中间，落点可控——本质是给生成加约束条件。可以结合实例：本项目里"宣布死亡时人已经被盖上白布"的穿帮，就是终点没钉死造成的。

**Q6：文本编码器为什么这么大（51 GB）？**

 要点：Qwen3-VL 32B 是多模态大模型，要同时理解文字提示和参考图，参数量决定体积（32B × 2 字节 ≈ 64 GB 量级的 BF16）；它也是显存不够时第一个被量化/卸载到内存的部件。

**Q7：BF16、INT8、NVFP4 有什么区别？为什么不用量化版省钱？** 

要点：数值精度不同，精度低体积小速度快、细节损失；满血版为画质，量化版为回退/试错。能说出"文本编码器 int8 版 27.1 GB"这种实数最加分。

**Q8：LoRA 是什么？Turbo LoRA 为什么能加速？** 

要点：LoRA 是低秩小补丁，不动主干，只训练/挂载少量参数；Turbo LoRA 通常是对采样过程做步数蒸馏训练出来的，把 20 步左右的去噪压到 8 步，用质量换速度，所以正式生产关掉。

#### C. 工程类

**Q9：为什么选 Colab，不买卡/租服务器？** 

要点：成本结构——本地卡（4060 8G）跑不动 124 GB 权重；租云 GPU 按小时贵；Colab Pro 订阅自带 CU 池，大显存实例（G4 约 96G）是能装下满血版的最低成本选项。补一句代价：会话会被回收、要做持久化设计。

**Q10：Colab 断连丢数据怎么解决？** 

要点：权重与产出全部软链云盘，断连只丢正在生成的那一条；纪律：页面常开、本机不睡眠、一集批量跑完；断后先查云盘存量再决定重排范围。有镜7夜跑断连、镜2重排的真实案例可讲。

**Q11：隧道是什么？为什么链接每次都变？** 

要点：云实例无公网入口，cloudflared 建出站隧道，Cloudflare 分配临时域名（trycloudflare），重启即换；这个链接等于 ComfyUI 的后台入口，不能外传；生产环境应换固定域名隧道加访问控制，或自有服务器。

**Q12：成本怎么算？一集多少钱？** 

要点：按 CU——G4 实测 10.05 CU/小时，单镜（4–6 秒素材）渲染约 4–6 分钟＋首镜权重加载约半小时；按镜头数可估一集 CU 消耗；对比商用 API 按秒计费（Seedance 等）是数量级差异。另一笔隐性成本是返工：本项目第一版因剧本逻辑问题整幕重做，所以"先改剧本和静图、再烧显卡"本身就是省钱手段。数字宁可说"我按 CU 记过账"，别编精确人民币。

#### D. 延伸与态度类

**Q13：和 Seedance/可灵这些商用工具比，你这套的意义？** 

要点：商用 API 快但贵、不可控（参数黑盒）；开源自建可控、可改、边际成本低，代价是工程复杂度。意义在"把生产能力握在自己手里"。

**Q14：版权和合规怎么考虑？** 

要点：故事原创（借结构不借情节、人名信物全原创）；模型许可证要看属地与商用条款（H3 社区许可证的地域提示我注意到并记录了，商用前逐条核对）；画面里的文字（屏幕、胸牌）后期添加，避免模型生成乱码；发布时标注 AI 合成内容。

**Q15：如果继续做，你会改进什么？** 

要点：

1. 首尾帧＋链式续拍：下一镜首帧＝上一镜实际末帧，在 ComfyUI 里搭成一张按镜头顺序连起来的节点图。
2. 对白口型：H3 直出口型在正脸中近景效果好，躺姿、侧脸会失效，说话镜头统一改成正脸中近景。
3. 验收清单脚本化（抽帧、查音轨、查"这镜有谁"）。
4. 固定隧道/自有节点降断连；工作流参数做成配置表。

**Q16（新增，建议准备）：你是怎么用多个 AI Agent 协作的？** 

要点：按擅长分工——Claude 写剧本和分镜，Gemini 打磨镜头语言和提示词，Codex 出定妆图、关键帧和做技术调研，另一个 Agent 负责渲染、审片和剪辑；人只做审批和最终判断。规则：发给 Agent 的每条指令先经人审原文。坑：两个 Agent 都写了剧本，必须指定唯一主版本，否则会互相打架。

**Q17（新增，建议准备）：讲一个你踩过的具体坑。** 

推荐讲"主角提前出现"：提示词里写了固定站位句，提到了主角，参考图也放了他，模型就把还没入场的主角画进了前两个镜头。定位到原因后定规则：不在场的人不放参考图，并在提示词写明"不在房间里"，重渲后解决。

这个例子能同时说明：模型照输入执行、问题在输入、你会定位原因并沉淀成规则。
